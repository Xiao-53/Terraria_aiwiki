# Terraria AI Wiki — 执行计划规范

本文件只规定 WSL Codex CLI 何时创建计划、计划存放方式、最低内容和执行生命周期。项目 Phase 的目标、依赖与顺序由 `docs/architecture/ARCHITECTURE-v0.6.md` 定义。

计划文件是跨 Codex CLI 会话的持久状态来源。不得依赖桌面端面板、聊天内临时计划或未写入工作区的隐藏状态。

## 何时必须创建计划

满足以下任一条件时，在实施前创建并维护执行计划：

- 属于 Master Architecture 中的任一 Roadmap Phase；
- 需要跨模块/平台协调或跨会话跟踪；
- 改变数据库、索引、数据包、抓取、更新、迁移或 P0 能力；
- 改变公共接口、用户流程、依赖、构建、打包或平台 Runtime；
- 包含删除、不可逆迁移或难以一次回退的操作；
- 存在影响方案或安全边界、需实验、PoC 或用户选择消除的重要不确定项。

简单、局部、低风险且不改变公共行为的修改无需单独建计划，即使涉及多个文件或需要代码阅读。

## 创建前必须读取

按 `AGENTS.md` 的上下文规则读取方案所依赖的证据；Phase 工作还须核对前置结果与未完成事项。不能只凭任务描述或架构图推定实现。

事实、推断、假设、已决定事项和待确认事项必须分开记录。

## 存放、命名与状态

一个进行中的变更使用一个独立目录：

```text
openspec/changes/<change-id>/
└─ plan.md
```

- Roadmap Phase 必须使用 Master Architecture 指定的 `phase-XX-<name>`。
- 非 Phase 工作使用简短、稳定、可识别的 kebab-case change id。
- 相关提案、规范增量或决策草案与该 change 关联，不另建重复计划目录。
- 计划默认由 WSL Codex CLI 在 `/mnt/c/Users/Xiao/mypython/terraria_aiwiki` 下维护；需要 Windows 验证的步骤必须单独标注执行环境。

计划状态：

```text
draft → approved → in-progress → completed → archived
```

- `draft`：正在调查或等待关键选择，不得据此修改业务源码。
- `approved`：范围和方案已获得用户明确批准；用户明确要求直接实施某项工作时，可将该范围视为已批准，但不得扩展授权。
- `in-progress`：正在执行，按实质进展与决策更新计划。
- `completed`：目标已完成、验证已记录、遗留项已说明。
- `archived`：把已完成 change 移入 `openspec/changes/archive/<change-id>/`。

未完成或未验证的 change 不得归档为完成。生成计划本身不等于获得实施后续 Phase 的授权。

## 计划最低结构

```markdown
# <变更名称>

- 状态：draft | approved | in-progress | blocked | completed
- Phase：<Roadmap Phase；非 Phase 写“无”>
- 执行环境：WSL Codex CLI；Windows/Android 验证需求
- 创建日期：YYYY-MM-DD
- 最后更新：YYYY-MM-DD
- 范围：<能力域、模块或平台>
- 关联架构/规范/ADR：<路径或“无”>

## 背景与当前证据
说明用户问题、实际读取过的代码和当前可验证行为；区分事实与假设。

## 目标与完成定义
列出可验收结果和进入下一阶段的门槛。

## 前置条件
列出前置 Phase、环境、数据、外部授权和未完成事项。

## 范围与非目标
明确允许修改、禁止触碰和留给后续 Phase 的内容。

## P0 / 兼容性影响
列出受影响的 Existing Core Capabilities、数据、平台与保护措施。

## 方案与待决问题
说明拟采用方案、替代方案、证据、PoC 和需要用户确认的决策点。

## 文件变更
基于真实代码列出 ADD / MODIFY / KEEP / REMOVE candidate 及理由。

## 执行步骤
- [ ] 步骤：涉及文件；预期结果；验证方式；回退点。

## 验证与回归计划
按 AGENTS.md 的风险规则列出必要检查、覆盖的风险、执行环境与完成条件；不默认罗列全量测试或 smoke，不为范围外平台建立检查。

## 风险与回退
记录数据、兼容、依赖、性能、平台、打包、删除风险和恢复方法。

## 进度记录
按日期记录完成项和下一步。

## 发现、偏差与决策
记录新事实、计划偏差、原因和已确认选择；长期选择关联 ADR。

## 验证结果
记录实际执行的检查、结果和未验证事项。

## 完成摘要
总结最终行为、剩余风险和后续事项。
```

这是内容参考，可合并或省略不适用章节；保留范围、完成条件、关键风险/回退、进度和验证证据。

## 执行纪律

1. 目标必须可验收；不得用“优化一下”“完善功能”等模糊描述替代结果。
2. 在有实质进展或决策变化时更新计划，保持跨会话可继续，不必逐个工具调用记账。
3. 先复用现有能力，再考虑局部修正、薄包装、必要抽取和最后重写。
4. 计划中的文件清单必须来自真实代码阅读；不得凭架构概念虚构类、接口或 project。
5. 新事实推翻原方案时，先更新计划和理由，再继续实施。
6. 不得借计划扩大任务范围、跨过前置 Phase 或提前建设后续扩展。
7. 涉及删除、数据语义、P0、平台或不可逆变化时，必须有显式决策和可执行回退。
8. 无法在当前环境执行的 Windows 或 Android 目标平台验证必须如实记录，不得推定通过；不为范围外平台建立验证任务。
9. 标记 `completed` 前检查实际文件差异、验证证据、规范/ADR 更新、临时文件和源码仓库状态。
10. WSL 中的 `dotnet`、静态检查或源码分析不得记作 Windows .NET/Avalonia 客户端构建、运行或打包通过；验证记录必须写明实际执行环境。

## 计划与其他文档的关系

- Phase 目标、依赖或 P0 变化：先更新 Master Architecture。
- 能力契约变化：更新 `openspec/specs/`。
- 长期技术选择：确认后新增或更新 `docs/adr/`。
- 当前 Phase 的 SQL、接口、文件、测试、依赖和打包细节：只写入该 change/plan。
- README 和 INIT 只更新入口、状态或路径，不复制计划正文。
